# Iteration 2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Place three persistent random slimes on distinct traversable tiles, defeat each independently, and restore the same placements on Restart.

**Architecture:** Store stable slime IDs and positions in a versioned world definition. Select placements from eligible terrain without replacement; bind each battle to its encounter ID. Upgrade older checkpoints once, preserving their original encounter and progress, and render/count only living encounters.

**Tech Stack:** Existing TypeScript, Phaser, Vite, Vitest, Playwright, and GitHub Pages; no additional packages expected.

**Spec:** `docs/superpowers/specs/2026-11-17-iteration-2-design.md`, approved November 17, 2026.

## Global Constraints

- Defeated slimes remain gone until Restart.
- Retain the accepted random world dimensions, three-tile scrolling buffer, touch/keyboard input, and battle rules.
- New Game creates exactly three stationary slime placements on distinct traversable tiles, excluding the hero's starting tile.
- Restart preserves world dimensions, terrain, and the same three slime positions.
- Save/Continue preserves the exact placements and each defeated state.
- The old far-corner path remains terrain decoration; paths do not promise to lead to each random slime.

No enemy movement, exploration respawn, minimum-distance rule, new battle abilities, minimap, or new assets. Native execution is already selected; retain it. Do not start another cloud chat without an owner request.

## Review Focus

1. Defeating slime2 or3 must not clear slime1 or any other encounter, and Run must preserve all placements/progress (Task 2).
2. A constant RNG must terminate with three distinct valid positions; adjacent/path positions remain eligible (Task 1).
3. Failed migration writes and repeated title refresh/Continue must not repeatedly reroll placements within the session (Task 1).
4. Partial progress and a hero standing on a defeated encounter must reload safely; invalid IDs/overlaps/active-encounter positions must be rejected (Tasks 1 and4).
5. Random encounters must not make old navigation tests flaky; scrolling/input/rotation guarantees remain covered with deterministic fixtures (Tasks 3–4).

## Shared contracts

- In `types.ts`, export `SLIME_IDS = ['slime-1','slime-2','slime-3'] as const`; derive `SlimeId` from that tuple. `SlimePlacement = { id: SlimeId; position: Position }`.
- Add `WorldGeometry = { layout: 'woodland' | 'legacy-expanded'; width: number; height: number }`. `WorldDefinition = WorldGeometry & { version: 2; slimes: SlimePlacement[] }`.
- `Checkpoint` becomes version3; its other properties remain world, position, hp, completedEncounterIds. Type completed IDs as `SlimeId[]` after runtime validation.
- Keep the world's array of all three placements even when defeated. Never mutate positions or splice defeated entries from world data.
- In `world.ts`, keep `getLandmarks(geometry: WorldGeometry)` and existing terrain rules; its fixed `encounter` point is now only the decorative path endpoint and the original encounter location for migration. Gameplay must use saved slime placements instead. Make movement/walkability and viewport inputs accept WorldGeometry so terrain/camera tests do not need encounter fixtures.
- `generateWorld(random: () => number = Math.random): WorldDefinition` draws width/height as before, then chooses three slime positions.
- `placeSlimes(geometry: WorldGeometry, preserved: SlimePlacement[] = [], excluded: Position[] = [], random: () => number = Math.random): SlimePlacement[]` fills the three known IDs, preserving supplied entries. Enumerate eligible cells row-major; exclude start, preserved positions, and explicit exclusions; choose uniformly from the remaining list and remove each selection. A supplied constant RNG0 terminates. Reject insufficient eligible cells with RangeError; do not retry indefinitely. RNG contract is finite draws in[0,1).
- `getLivingEncounterAt(checkpoint: Checkpoint, position: Position): SlimePlacement | null` and `getRemainingSlimeCount(checkpoint: Checkpoint): number` share encounter/completion lookup. Keep `createCheckpoint(world)` resetting position, HP and completed IDs while retaining the exact world.

### Task 1: Persistent random placements and old-save upgrade

**Files:** Types/world/save, new legacy-save module, main migration handling, unit tests, and mechanical consumer/fixture changes required by the schema. Keep existing one-slime battle behavior working for its fixture until Task2 binds every identity; do not deploy intermediate commits.

**Interfaces:** Save under `simple-rpg.save.v3`. `parseSave(raw: string | null): Checkpoint | null` accepts version3 only. `migrateOlderSave(raw: string | null, random: () => number = Math.random): Checkpoint | null` accepts validated v1/v2 and returns v3. `loadSave(storage: Pick<Storage,'getItem'>, random: () => number = Math.random)` retains `{ checkpoint, status, migrated }` and adds `source: { key: string; raw: string } | null` so main can cache a migration by exact source content. `saveGame` keeps its guarded-write boolean contract.

Pin the cache interface before coding: export `MigrationSource = { key: string; raw: string }` and `MigrationResolver = (source: MigrationSource, create: () => Checkpoint | null) => Checkpoint | null` from save.ts. The full loader signature is `loadSave(storage: Pick<Storage,'getItem'>, random: () => number = Math.random, resolveMigration: MigrationResolver = (_source, create) => create())`. Invoke the resolver only for the selected older-format source. In legacy-save.ts export `parseOlderSave(raw: string | null): LegacyCheckpoint | null`, where LegacyCheckpoint is the validated version2 shape from Iteration1; v1 parsing translates into that intermediate representation. migrateOlderSave consumes it and constructs the new world/placements.
