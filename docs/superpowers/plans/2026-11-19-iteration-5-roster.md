# Iteration 5: Character Roster Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Native execution remains selected: implement inline, with one final independent whole-branch review.

**Goal:** Support ten independently saved character playthroughs with creation, viewing, resuming, confirmed deletion and penalty-free Restart.

**Architecture:** Replace the historical single-adventure loader with a version-6 combined roster. Pure validation and immutable roster mutations sit behind a serialized storage service; the application tracks an active slot ID/revision and merges only that slot into the latest document. A roster component owns selection/detail/confirmation screens, reusing character creation and the existing adventure renderer.

**Tech Stack:** Existing TypeScript, Phaser, Vite, Vitest, Playwright and browser localStorage/Web Locks. No new runtime dependencies or hosting changes.

**Spec:** `docs/superpowers/specs/2026-11-19-iteration-5-roster-design.md` (owner approved).

## Global Constraints

- Maximum ten independent slots, stable insertion order, each containing its character/build, world and progress. No auto-resume on load. Duplicate names permitted; identity is by unique ID.
- Creating a character immediately starts its playthrough; no standalone templates or editing. Cancel/refresh discards the draft. At ten, creation blocks but Resume/View/Delete/Restart remain available.
- Attributes start at 1, plus exactly 5 points, integer ratings 1–5, total 8. Skills start at 0, plus exactly 5 points, integer ratings 0–5, total 5; Combat 0 allowed. Names trimmed/nonblank, maximum 24 UTF-16 code units, rendered as text.
- Preserve derived stats, opposed dice, three 3-Health/3-dice slimes, world generation, collision, three-tile sight, safe checkpoint behavior, victory healing, Run Health retention and 300 ms battle gates.
- Defeat persists separately from the safe checkpoint. Restart preserves ID/order/build/map/slime placements, restores full derived Health, resets encounters, clears defeat, and adds no penalty.
- New combined saves only: ignore all v1-v5 keys, no migration or automatic import. Production and acceptance use separate namespaces. Invalid data requires confirmed reset; unavailable reads never authorize replacement.
- Every writer uses the per-namespace Web Lock and one setItem of a validated combined document. Recheck capacity/target revision inside the transaction; preserve unrelated slots and reject stale/deleted targets.
- Creation/deletion/Restart/reset enter success only after durable saving. Failure retains draft or relevant screen and retry/back path. Warn before leaving unsaved in-memory progress. Read-only browsers can resume readable active slots but cannot mutate the roster or Restart.
- Return to characters from exploration, victory and defeat; no battle exit command. Reload during battle retains the existing last-safe-checkpoint behavior. All-three-slimes completion remains resumable.
- No leveling, XP, classes, specializations, gear, resource spending, import/export, accounts or cross-device sync.
- Follow accepted mockups without preview controls/sample data/frame. Minimum 48px touch controls, safe long-name wrapping, vertical scrolling, no horizontal overflow at 320x568, 390x844 and 844x390, large-text and keyboard accessibility.
- Native execution on `codex/iteration-5`; reuse the existing normal checkout. Finish with verified commits and a draft PR. Deployment/merge require subsequent owner direction.

## Review Focus

1. Two tabs compete for the tenth slot or mutate different slots: exactly ten survive and neither unrelated adventure loses progress (Tasks 2/4).
2. A slot is deleted/restarted/updated while another tab plays or confirms deletion: stale actions never recreate or overwrite it, even if name/build are identical (Tasks 1/2/4).
3. Storage fails at creation, deletion, defeat, Restart, reset or return: no false success, ghost slot or silent loss; recovery remains usable (Tasks 2–4).
4. Invalid combined data alongside valid old saves, duplicate IDs/names and malformed nested worlds: no migration, partial salvage or wrong-target deletion (Tasks 1/2/4).
5. Refresh/focus/storage events, physical double clicks, held gestures and keyboard reading while forms/confirmations are open: drafts/focus remain stable and destructive actions require fresh intent (Tasks 3/4).

## File responsibilities and shared contracts

- `src/game/types.ts`: retain internal `Checkpoint.version:5` and existing battle/session types; introduce roster UI commands only at the application boundary. A v5 checkpoint nested in a v6 document is internal validated data, not permission to load an old v5 storage key.
- New `src/game/roster.ts`: `RosterSlot = { id:string; revision:number; status:'active'|'defeated'; checkpoint:Checkpoint }`, `RosterSave = { version:6; slots:RosterSlot[] }`, `MAX_CHARACTERS=10`. IDs are canonical UUIDs produced by `crypto.randomUUID()`; positive safe-integer revisions start at 1 and increment on every successful slot update/Restart, including a reset to otherwise identical values. Reject revision overflow. Never mutate caller-owned snapshots.
- `src/game/save-validation.ts`: move the still-needed `parsePlacedProgress(value:Record<string,unknown>,maxHp:number)` and placement validation out of `legacy-save.ts` without relaxing their current world/position/completion rules. Return the current world/position/hp/completedEncounterIds shape or null.
- `src/game/save.ts`: export `parseCheckpoint(raw:string|null):Checkpoint|null` (current v5 validation), `parseRoster(raw:string|null):RosterSave|null`, `loadRoster(storage:Pick<Storage,'getItem'>):RosterObservation`, `writeRoster(storage:Pick<Storage,'setItem'>,save:RosterSave):boolean`. `RosterObservation={status:'ready'|'empty'|'invalid'|'unavailable';raw:string|null;roster:RosterSave|null}`; missing means an empty v6 roster, invalid/unavailable have null roster. Canonicalize by rebuilding validated fields; read only the new key. Remove single-save migration/load/save/signature APIs after all consumers are converted.
- `src/game/save-keys.ts`: current key becomes `simple-rpg.save.v6` or `simple-rpg.acceptance.save.v6`; do not expose fallback keys to the loader. Remove `src/game/legacy-save.ts` after extracting shared validation; remove historical-only `isStarterCharacter` if no live consumers remain.
- New `src/game/roster-store.ts`: `createRosterStore(storage:Storage|null,locks:SaveLocks|undefined,key:string):{read():RosterObservation; transact(command:RosterCommand):Promise<RosterResult>}` using existing `createSaveCoordinator`. `RosterCommand` discriminants: `create {character:Character}`, `update {id:string;expectedRevision:number;checkpoint:Checkpoint;status:'active'|'defeated'}`, `restart {id:string;expectedRevision:number}`, `delete {id:string;expectedRevision:number}`, `reset {expectedRaw:string}`. The factory may accept an optional fourth dependencies object `{newId?:()=>string;newWorld?:()=>WorldDefinition}` for deterministic unit tests; production defaults use browser UUID/world generation.
- `RosterResult` is `{kind:'saved';roster:RosterSave;slot:RosterSlot|null}` or `{kind:'full'|'stale'|'missing'|'invalid'|'unavailable'|'write-failed';observation:RosterObservation}`. Only create/update/restart return a non-null successful slot; delete/reset return null. A failed read is unavailable; invalid non-reset operations return invalid. No locks means unavailable for all mutations. Reset accepts invalid raw only and compares exact raw inside the lock. All mutations return fresh snapshots.
- `src/game/session.ts`: preserve pure combat/movement rules; add `Action {type:'returnToRoster'}` to return to title from exploration/victory/defeat. Add `Action {type:'resumeDefeat';checkpoint:Checkpoint}` for title→defeat without transient rolls. The store uses `createCheckpoint(saved.world,saved.character)` for Restart; application enters exploration with the saved result rather than applying an optimistic reset.
- New `src/view/roster.ts`: `mountRoster(root:HTMLElement,callbacks:{onCreate():void;onResume(id:string):void;onRestart(id:string,revision:number):void;onDelete(id:string,revision:number):void;onReset(raw:string):void}):{update(observation:RosterObservation,canMutate:boolean):void;setPending(pending:boolean):void;showMessage(message:string):void;destroy():void}`. Own list/detail/delete/reset screens and remembered confirmation source. Updates preserve view/focus when its target survives; target changes renew confirmation with a fresh gesture, target removal returns to list. Reset is offered only for invalid readable data.
- `src/view/character-creation.ts`: replace overwrite-confirmation callbacks with `onBegin(character)`/`onCancel()`, retain `setPending`, add `showMessage(message:string):void`. Allocation, composition handling and draft retention stay intact. Capacity/save failures must not remount it.
- `src/view/ui.ts`: mount title roster or creation as components; retain adventure/character/roll rendering and persistent announcements. Expose `setRoster(observation,canMutate)`, `setCreationPending(pending)`, `showCreationMessage(message)`, `completeCreation()` and callbacks wired to the store commands. Add Return to characters and a safe Keep playing/Discard unsaved progress confirmation when requested by main; destructive/discard confirmation uses a 300 ms fresh-gesture gate shared with roster confirmation (new `src/view/confirmation.ts`). Retain main's `render(state,status)`/busy/focus behavior; names never interpolated as markup.
- `src/main.ts`: owns selected slot ID/revision, game state, dirty/stale status and async dispatch. Read newest slot on Resume; never writes merely for reading/selection. Store transactions own durable mutations, with no nested lock requests. On autosave failure keep in-memory state dirty and expected revision unchanged; a later successful slot write clears dirty. On stale/missing stop writes until returning/resuming fresh. Roster changes on focus/storage refresh without unmounting drafts. Scene renders title when roster is visible; view state remains outside Phaser.
- Tests: `tests/roster.test.ts`, `tests/roster-store.test.ts`, `e2e/roster.spec.ts`, `e2e/roster-concurrency.spec.ts`, `e2e/roster-recovery.spec.ts`; adapt current session/save/creation tests and e2e fixtures/helpers. Remove migration-only scenarios rather than preserving obsolete behavior. Update `scripts/verify-deployment.mjs`, README and a new Iteration 5 status note.
