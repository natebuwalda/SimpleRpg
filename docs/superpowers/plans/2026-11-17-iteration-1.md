# Iteration 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Explore a saved, randomly sized woodland world through a scrolling 10-by-10 view that keeps three visible rows/columns ahead of the hero.

**Architecture:** Add a versioned world definition to checkpoints so movement, encounter placement, rendering, and validation agree on the same map. Calculate the buffered viewport with pure TypeScript, then draw only its visible tiles. Keep existing HTML controls, battle composition, and production hosting.

**Tech Stack:** Existing TypeScript, Phaser, Vite, Vitest, Playwright, and GitHub Pages; no additional packages expected.

**Spec:** `docs/superpowers/specs/2026-11-17-iteration-1-design.md` (approved November 17, 2026).

## Global Constraints

- Keep the accepted phone controls, collision, battle loop, local saves, and responsive panel layout.
- Choose width and height independently, uniformly from integer sizes 20 through 40, on New Game.
- Randomize dimensions only in this iteration.
- Include a three-tile-thick impassable forest border within the world dimensions.
- Use immediate, whole-tile camera shifts to match current one-tile movement.
- Keep the three-tile margin as a named configurable value with default 3.
- Continue must restore the same world and derive its camera offset from position.

No fog, randomized terrain, additional enemies, infinite generation, new settings screen, zoom-to-fit, stack changes, or alteration of the battle rules.

## Review Focus

1. Old valid saves must migrate without lost HP, completion state, or relative landmark positions; a corrupt new save must not silently resurrect an older checkpoint (Task 1).
2. Reversing direction inside the viewport must not recenter or jump; collision must leave the viewport unchanged (Tasks 2–3).
3. All four playable map edges must preserve three full visible tiles and never expose blank outside-world space (Tasks 2–3).
4. Escaping, winning, refreshing, and continuing far from the original screen must restore world position and a valid view (Tasks 3–4).
5. Rotation, repeated input, and two tabs must preserve the existing input/save guarantees while using the new checkpoint format (Task 4).

Shared types:

```ts
type WorldDefinition = {
  version: 1;
  layout: 'woodland' | 'legacy-expanded';
  width: number;
  height: number;
};
type Checkpoint = {
  version: 2;
  world: WorldDefinition;
  position: Position;
  hp: number;
  completedEncounterIds: string[];
};
```

Keep `Position`, `Direction`, `BattleState`, and GameState variants. Change the domain `newGame` Action to require `world: WorldDefinition`. Export `UiAction = Exclude<Action, { type: 'newGame' }> | { type: 'newGame' }` for UI intents; `main.ts` supplies a generated world before calling `transition`. Continue already carries a full checkpoint. Restart resets progress in the same world, avoiding an unrelated map change after defeat.

World contracts in `world.ts`:

- `generateWorld(random: () => number = Math.random): WorldDefinition`: two independent draws in [0,1), each dimension `20 + floor(draw * 21)`, layout woodland, version1. Never generate during render/Continue/ordinary movement.
- `getLandmarks(world: WorldDefinition): { spawn: Position; obstacle: Position; encounter: Position }`.
- `isWalkable(world: WorldDefinition, position: Position): boolean`.
- `move(world: WorldDefinition, position: Position, direction: Direction): Position`: return original position when blocked.
- `atEncounter(world: WorldDefinition, position: Position): boolean`.
- `createCheckpoint(world: WorldDefinition): Checkpoint`.

Builder decisions: fresh woodland spawn (3,3), obstacle (6,5), slime (width-5,height-5). Place its path from spawn horizontally to the slime column, then vertically to the slime. The slime is deliberately beyond the original screen and reachable. Legacy-expanded is exactly 20x20 with spawn (4,4), obstacle (6,5), slime (8,6): the old spawn/obstacle/slime translated by (+2,+2). Its path follows the same spawn-to-slime rule. Walkable coordinates are integers from3 through width-4 / height-4 inclusive except the obstacle. Path appearance never determines collision.
